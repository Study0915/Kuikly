# Shape with AI KuiklyUI 题面与导师讲解报告（人读版）

## 1. 先说结论

这次实战不是在比谁更快做出一个普通股票列表或聊天页，而是在一个可运行、完整的 Kuikly Demo 上，比三件事：

1. 基础链路是否完整可靠；
2. 是否沉淀出可复用、可扩展的业务组件；
3. 是否设计出有意思、可演示的 “AI × UI” 信息载体和交互。

正式评分是 **功能完整性 40% + 工程设计 25% + AI 场景设计 25% + 加分项 10%**。导师口头说明没有改变这个计分表，但反复强调：基础列表、详情、输入和发送是大家都容易做到的“地板分”；真正拉开差距的是后两个 25%，尤其是通用组件与 AI 信息承载方式。

因此，最优策略不是先做一个庞大系统，也不是把大量时间投入真实行情 API、真实大模型或全平台适配。应先闭环，再选一个清晰的创新母题，把它做完整、做成组件、做出状态、做出交互，并用稳定录屏证明。

## 3. 两个 Task 的准确理解

### 3.1 Task 1：AI 股票行情原型 Demo（三星）

正式 Must：

1. 首页行情列表：名称、代码、最新价、涨跌额、涨跌幅；可滚动；可点击进入对应详情。
2. 个股详情：名称、代码、最新价、涨跌幅、最高价、最低价、成交量。
3. 详情内有可见的 AI 分析与解读模块。形式发散，可围绕买卖点位、操作提示、趋势判断、风险提醒、信号解读、行情总结等设计。

导师真正想看的不是“AI 输出一段买入文本”，而是客户端如何承载 AI：卡片、标签、解释区、风险区、趋势图上的信号标记、可展开证据、情景切换等都可以。数据和模型不必真实，Mock 可以；关键是创意、交互与代码组织。

### 3.2 Task 2：AI 股票问答应用 Demo（四星）

正式 Must：

1. AI 聊天主页：输入、发送、会话记录。
2. AI 返回内容：支持 Markdown，并至少有一种股票/指数/行情相关的非文本业务内容。
3. 至少一个聊天结果可点击进入详情承接页；详情展示基础行情、走势区域，以及摘要或 AI 解读。

导师强调聊天结果不能只吐纯文字。结构化股票卡、指数卡、迷你趋势、组合型结果、可操作建议或其他业务组件都可以。这里的高分点仍是“内容形态 + 交互 + 组件化”，不是接入多强的模型。

## 4. 正式评分与口头校准

| 维度 | 正式权重 | PDF 考察点 | 导师口头校准 |
|---|---:|---|---|
| 功能实现完整性 | 40% | 页面闭环、需求覆盖、状态处理完整性 | 是必要地板，但基础功能不太能区分选手；必须先稳定闭环 |
| 代码质量与工程设计 | 25% | 分层、可维护、扩展、规范；可孵化通用组件 | 反复强调“比较好的通用组件”；组件应真正可复用，不只是拆文件 |
| AI 场景设计能力 | 25% | 与股票业务自然结合、能力可演示、创新场景 | 重点是 AI 信息的 UI 载体和交互，不是模型或分析文本本身 |
| 加分项 | 10% | 多端、真实 API、体验优化 | 欢迎但不应喧宾夺主；鸿蒙、真实数据等不是主权重 |

### 4.1 对时间投入的含义

- 40% 功能分并不意味着 40% 以后全部用来堆页面。基础闭环一旦稳定，新增普通列表项的边际收益很低。
- 25% 工程与 25% AI 场景共占一半，而且是导师口头最重视的区分项。
- 10% 加分项只能在前三项稳定后做。真实 API、更多平台或复杂动画不能补救不可运行、缺链路或没有核心创意。

## 6. 导师反复强调的高优先级事项

### 6.1 高置信度，直接作为流程门禁

1. **代码必须真的能运行。** 导师说这是“很关键、非常关键”。
2. **基础功能必须完整闭环。** 但它是地板，不是最大区分项。
3. **孵化通用组件。** 页面、组件、数据、状态应分层，组件要可维护、可扩展。
4. **AI × UI 的交互载体。** 重点不是模型能力或文本质量，而是如何把 AI 信息自然放进股票场景。
5. **创新要能演示。** 不能只有设计稿或 README；要有完整交互和录屏。
6. **说明文档要主动讲亮点。** 让评审快速理解组件、AI 场景和工程取舍。
7. **不要把范围一开始做得过大。** 先完成小闭环，再逐步增加高价值能力。

### 6.2 中置信度，作为策略建议

- Mock 行情和 Mock AI 可以拿来证明交互；不必为了“真实”牺牲稳定性。
- issue 阶段组件和其他开源实现可以参考，评价重点在结合、改造与工程质量。
- 真实 API、多端覆盖、体验打磨属于加分，前三个主维度稳定后再投入。
- 工作量和难度会被考虑，但不是“堆功能越多越高分”。

### 6.3 尚未确认，不能写成确定事实

- 截止日期是否为 9 月 14 日：导师现场说“好像/不太确定”。
- Task 1 与 Task 2 是否严格独立赛道、各取最高：导师说按其理解分开评分，并表示会再向组委会确认。
- 是否必须在同一交付中完成两题：PDF 交付页把 “Task 1 行情 + Task 2 问答核心功能” 写在同一源码完整性条目，但 Q&A 又把“两个都做”描述为有余力时的选择，存在书面/口头歧义。
- 组队与个人奖项的最终规则、三个奖项如何分配：现场表达存在不确定词。

这些事项应进入 `导师待确认问题`，不能据此做不可逆的范围决策。

## 7. 对当前仓库工作流的诊断

当前流程的优势：

- 题面 Must 与历史 Issue/归档已经隔离；
- 有任务卡、唯一写入者、状态机和 `code/tests/evidence/learning` 四门；
- 能区分 Mock、构建、浏览器交互、设备运行和未验证平台；
- Task 1 先垂直闭环、Task 2 后启动，能控制范围。

当前缺口：

1. 只在一句话里提到“创新”，没有正式的 40/25/25/10 评分映射。
2. 任务卡没有要求写清“本切片拿哪一项分、核心组件是什么、AI 载体是什么”。
3. `learning` 报告偏代码学习，没有要求形成评审可读的亮点叙事。
4. `evidence` 有构建与截图，但缺最终评审视角的端到端演示脚本和录屏清单。
5. 当前把所有图表都放到 Optional 是正确的范围控制，但还需允许“最小趋势 + AI 标注”作为评分高杠杆候选，而不是默认把所有视觉联动都排除。
6. 没有区分 Feature VERIFIED 与“可投稿/可评审”的最终交付状态。

## 8. 推荐的高分实现母题（不是替用户决定范围）

### 8.1 Task 1：可解释行情洞察组件

一个有竞争力且不过度膨胀的方向是 `MarketInsightSurface`：

- 输入：行情快照、若干趋势点、结构化洞察；
- 输出：风险等级、结论、理由、置信/时效、可展开证据；
- 展示：摘要卡 + 风险标签 + 趋势区域的信号标记；
- 状态：loading / ready / unavailable / stale / disclaimer；
- 可复用：详情页、聊天结果卡或其他指数页面可共享同一数据模型/视觉语义。

它同时覆盖 AI 场景分、工程分和演示效果。这里的趋势区域可以很小，不要求先建设通用 K 线平台。

### 8.2 Task 2：结构化对话结果画布

一个高杠杆方向是 `ChatBlock` + `MarketResultCard` + 详情承接：

- 同一条 AI 回复由 Markdown、行情卡、风险提示、迷你趋势或操作入口组成；
- block 有显式类型和稳定数据，不从 Markdown 反解析；
- 卡片可点击进入正确详情，返回后会话保留；
- 失败、重试、长会话和未知实体有清楚状态；
- 同一 renderer 可渲染多个业务 block，证明组件扩展性。

### 8.3 两题共同的演示原则

- 开场 10 秒说明“我解决了什么交互问题”；
- 20-40 秒完成主链路；
- 20 秒突出核心组件与 AI 载体；
- 10 秒展示异常恢复或跨端一致性；
- 结尾说明 Mock/真实边界、技术亮点与非投资建议。

## 9. 最终评审自查表

### 功能 40%

- [ ] 所有题面字段与主链路可见、可操作；
- [ ] loading/empty/error/unknown/retry 不破坏闭环；
- [ ] 列表、详情、聊天、返回等状态真实可演示；
- [ ] Android/H5 声明与实际证据一致。

### 工程 25%

- [ ] 至少一个核心业务组件有明确输入、输出和状态合同；
- [ ] 页面、组件、数据、状态分层；
- [ ] 组件至少在两个场景、两种数据形态或两组 fixture 上证明可复用；
- [ ] 命名、目录、注释、测试和扩展点清楚；
- [ ] 没有为未来假想需求搭建庞大框架。

### AI 场景 25%

- [ ] AI 能力与股票业务自然结合；
- [ ] AI 信息不是单一静态文本；
- [ ] 用户能理解“结论、理由、风险、时效/数据边界”；
- [ ] 有至少一个有意义的交互或视觉联动；
- [ ] Mock/真实 AI 明确标记，演示不误导。

### 加分 10%

- [ ] 只在主链路稳定后增加真实 API、多端或体验优化；
- [ ] 新能力有真实运行证据；
- [ ] 不用未验证平台或 API 声明换取“纸面加分”。

### 交付

- [ ] 独立仓库可从说明文档启动；
- [ ] README 讲清项目、技术栈、架构、核心亮点、运行方式和限制；
- [ ] 录屏覆盖完整主链路、关键操作和 AI 载体；
- [ ] 评审不需要猜测入口、账号、数据来源或启动步骤。

## 10. 当前最合理的下一步

先不要直接扩大业务代码范围。先用本报告、`docs/evaluation-pipeline.md` 和 `docs/plans/_TASK-PLAN-TEMPLATE.md` 完成 `docs/plans/TASK1-PLAN.md` 中的四个竞赛决策：

1. 选定一个核心 AI 载体；
2. 选定一个要孵化的通用组件；
3. 定义它如何用真实交互证明，而不是只靠说明；
4. 定义 90 秒左右的最终演示主线。

四项经用户确认且 T1-PLAN 达到 `VERIFIED` 后，再把同一计划交给 OpenCode 进入 T1-CODE；随后按 TESTS、LEARNING 顺序推进，不再创建旧式 Feature 任务卡。
