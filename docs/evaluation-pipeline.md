# Kuikly Shape 高分评分约束

## 1. 作用

本文件只定义“怎样规划和证明高分”，不预先决定具体创新点，也不增加 `docs/REQUIREMENTS.md` 的题面 Must。活动顺序、角色和交接以 `docs/agent-workflow.md` 为准。

| 维度 | 权重 | 高分核心 |
|---|---:|---|
| R-FUNC | 40% | 页面闭环、题面覆盖、状态完整、实际可运行 |
| R-ENG | 25% | 清楚分层、可维护扩展、可证明复用的核心组件 |
| R-AI | 25% | AI 与股票业务自然结合，载体、交互和解释完整 |
| R-BONUS | 10% | 经验证的平台、真实 API 或体验优化 |

基础功能是得分地板；R-ENG 与 R-AI 是主要区分项。Bonus 只能在前三项稳定后投入。

## 2. 每份 Task PLAN 的强制评分表

Task 1、Task 2 总计划分别维护一张表：

| 维度 | 得分目标 | 计划实现 | 评审可见结果 | TESTS 直接证据 | SUBMIT 呈现 | 状态 |
|---|---|---|---|---|---|---|
| R-FUNC 40 |  |  |  |  |  | PLANNED |
| R-ENG 25 |  |  |  |  |  | PLANNED |
| R-AI 25 |  |  |  |  |  | PLANNED |
| R-BONUS 10 |  |  |  |  |  | NOT_STARTED |

状态只能使用 `PLANNED`、`SELECTED`、`IMPLEMENTED`、`VERIFIED`、`NOT_STARTED`、`DROPPED`。没有运行或测试证据时不能写 `VERIFIED`。

## 3. 创新决策门

具体创新点尚未决定时，Codex 在 PLAN 中提供 2-4 个候选：

| 候选 | 用户价值 | R-ENG 收益 | R-AI 收益 | 实现成本 | 风险 | 最小可演示版本 | Codex 建议 |
|---|---|---:|---:|---|---|---|---|
|  |  |  |  |  |  |  |  |

约束：

- 候选表只用于决策，不等于实现授权；
- 用户必须选择核心组件、AI 载体和删减线；
- 未选择时 PLAN 为 `WAITING_USER`，CODE 保持 `BACKLOG`；
- 选择结果写回 Task 总计划，不创建具体 Feature 任务卡；
- CODE 中如需改变创新方向，必须退回 PLAN 重新确认。

## 4. R-FUNC 40：完整性约束

高分不是“页面存在”，而是主链路可连续完成：

- 所有题面字段和交互有明确实现落点；
- loading、empty、error、unknown、retry 等适用状态有恢复动作；
- 至少使用两个实体或两组数据证明不是单例硬编码；
- Mock、构建、浏览器、APK、设备与未验证平台分别声明；
- TESTS 以实际命令和交互证据裁决。

## 5. R-ENG 25：核心组件约束

计划必须选定一个主要工程亮点。只有同时满足以下条件，SUBMIT 才能称其为“通用组件”：

1. 有聚焦的输入、输出与状态合同；
2. 页面、状态、领域数据和渲染职责分离；
3. 正常、边界与失败行为可独立测试；
4. 至少两个 caller、场景或数据变体实际复用；
5. 可配置范围清楚，不是无边界万能组件；
6. Android/H5 差异已验证或明确标记；
7. 当前 Kuikly 2.4.0 的 API 有 tag/source、编译或运行证据。

拆文件、改名为 `Component` 或只出现一个调用点，不构成复用证明。

## 6. R-AI 25：AI 信息载体约束

AI 场景不能只是一段静态文本。计划选定的载体至少覆盖：

- 结论：系统表达什么；
- 理由：依据是什么；
- 风险/不确定性：什么时候不应依赖；
- 数据时效：Mock、更新时间或来源边界；
- 交互：展开、比较、信号定位、情景切换、追问或进入详情中的至少一种；
- 恢复：缺数据、不可用或未知实体如何处理；
- 安全：不构成投资建议，不把 Mock 冒充真实预测。

模型可以是 Mock；载体、状态和交互必须真实运行并在演示视频中可见。

## 7. R-BONUS 10：启动约束

只有 R-FUNC 主链路通过、核心组件合同冻结、AI 载体可演示后，才能选择 Bonus。

真实 API、额外平台、复杂动画、通用图表或高级手势均可被放弃。时间不足时优先删除 Bonus，不削弱主链路、组件复用或 AI 载体。

## 8. TESTS 的评分证据

TESTS 报告必须把每个评分声明指向直接证据：

| 声明 | 最低证据 |
|---|---|
| common 逻辑正确 | 实际单测命令与结果 |
| Kotlin/JS 可编译 | `:shared:compileKotlinJs` 日志 |
| H5 可交付 | production bundle 日志 |
| H5 可交互 | 浏览器截图/录屏与主链路结果 |
| Android 可构建 | JVM tests + APK 路径/摘要 |
| Android 可运行 | 设备/模拟器信息与指定交互证据 |
| 组件可复用 | 两个实际 caller/场景及测试 |
| AI 载体完整 | 结论、理由、风险、时效、交互和恢复的运行证据 |
| 真实行情/模型 | 来源、时间、许可和运行日志；否则明确 Mock |

## 9. SUBMIT 的最终评分审查

SUBMIT 对两题分别检查 R-FUNC/R-ENG/R-AI/R-BONUS，不用一题证据替代另一题。最终 README 与视频必须让评审在短时间内看见：

1. 完整主链路；
2. 核心组件及复用；
3. AI 载体与有意义交互；
4. 至少一个边界或恢复状态；
5. 已验证平台、Mock/真实和投资风险边界。

任何“高分”判断都必须引用 TESTS 或 SUBMIT 直接证据，不以代码量、README 声明或历史归档替代。
