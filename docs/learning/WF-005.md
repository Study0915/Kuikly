# WF-005 · 题面视频理解与评分对齐管线学习报告

## 一句话目标

把“老师到底看重什么”从零散 PDF、视频和转写稿，变成后续每个 Agent 都能执行和验证的评分合同。

## 变更范围

- 实际修改：REQUIREMENTS、agent workflow、Task 1/2 readiness、任务/学习/handoff 模板、workboard。
- 实际新增：人读/AI 两版材料报告、55 条资料手册、评分管线、竞赛策略模板和 WF-005 四门文档。
- 未修改但复用：`code/tests/evidence/learning` 四门、任务状态机、Mock-first、平台证据分级与归档隔离。
- 明确非目标：业务编码、框架升级、真实服务、通用图表、外部发布。

## 调用链

```text
PDF + 视频画面 + 转写稿
  → 正式 Must / 正式权重 / 口头校准 / 未确认项
  → REQUIREMENTS
  → evaluation-pipeline
  → 竞赛策略卡
  → 详细计划与 Feature 任务卡
  → code/tests/evidence/learning
  → Rubric 独立复验
  → README + 演示视频 + 可运行交付包
```

## 状态变化

- 初始：仓库只有一句泛化的“创新性”，没有正式权重、AI 载体、通用组件或演示合同。
- 分析中：正式 PDF、视频口头强调和 Q&A 不确定项分别记录，避免互相覆盖。
- 完成：Feature 四门保持不变；评分层要求 R-FUNC/R-ENG/R-AI/R-BONUS 直接证据，并区分 Feature VERIFIED 与最终评审候选。
- 后续：用户先确认 Task 1 竞赛策略卡，再编写/确认详细主计划；未确认的组织规则由用户向导师/组委会核实。

## 关键 API 与设计原因

- Kuikly API：本任务未调用；资料手册只索引官方 List/Input/Canvas/Router 等资料，并要求对当前 2.4.0 做 tag/source/compile probe。
- Kotlin/KMP API：本任务未修改；工作流继续要求领域、状态和格式化优先放 commonMain。
- 为什么保留四门：它们已经很好地控制真实性和可复现性；问题是缺评分/演示覆盖，不是门的数量不足。
- 为什么增加竞赛策略卡：详细计划能回答“怎么做”，但不能自动回答“为什么这个差异点值得做、评审如何看见”。
- 被拒绝的替代方案：把图表、真实 API、全平台或强模型直接提升为 Must；这会违背题面和导师“不要做庞大范围”的口头强调。

## 测试与证据

- 执行命令及结果：`git diff --check` 通过；本地 Markdown links 通过；变更全部在 `docs/`；资料表 55 条；临时分析目录不存在。
- 截图/日志/构建产物：中间抽帧只用于分析，已删除；证据记录在 `docs/evidence/2026-08-21-shape-material-workflow.md`。
- Android 与 H5 差异：本任务没有运行业务；工作流明确二者构建/浏览器/设备分别留证。
- 未验证项：截止日期、两题是否分赛道/必须同时交付、组队/奖项规则；外部依赖在当前版本的真实兼容性。

## 评分贡献与演示

- 主评分维度：`R-ENG`
- 实际贡献：把组件合同、复用证明、版本探针、可访问性和评审交付固化到管线。
- 通用组件与复用证明：评分层同时服务 Task 1/2，但没有把两题的证据混为一体。
- AI 信息载体与用户价值：定义了结论、理由、风险、时效、交互、恢复和免责声明的完成条件。
- 评审可见证据：人读报告、AI 合同、资料手册和评分管线。
- 建议录屏片段：本任务不录业务 Demo；模板提供 90 秒脚本。
- Mock / 真实与投资风险边界：Mock 可证明交互，但必须标记，不能冒充实时预测。

## 易懂性检查

- 没看源码的 Kotlin/KMP 初学者能否复述：可以；先闭环，再做一个窄而深的 AI 载体和组件，最后用真实运行和视频证明。
- 仍需补充的概念：用户确认具体竞赛策略后，在 Task 1 详细主计划中给出文件级接口、状态与测试矩阵。
