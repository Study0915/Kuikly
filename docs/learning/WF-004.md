# WF-004 学习报告 · Task 分工与详细计划门

## 为什么要显式区分两题角色

Task 1 和 Task 2 仍使用相同状态机与四门，但“管线相同”不等于“默认写入者相同”。把角色按任务写入规则、readiness 和任务板后，Agent 可以直接从 Task ID 确定工作树：Task 1 在 Windows 由 Codex 主实现；Task 2 在 WSL Linux 原生克隆由 OpenCode 主实现。

## 调用链与状态变化

Task 1 的进入路径是：

`REQUIREMENTS → TASK1-DETAILED-PLAN → 用户确认 → Feature 任务卡 → Codex 实现 → 四门 → Codex 验收`。

Task 2 的进入路径是：

`Task 1 VERIFIED → Task 2 任务卡/OpenCode handoff → 用户确认 → OpenCode 实现并提交功能分支 → Codex Windows 复验 → 四门 → 用户集成`。

本次只改变协作控制面，没有改变页面、Provider、路由、Gradle module 或平台构建。T1-VERTICAL 从 `READY` 退回 `BACKLOG`，原因是新增的 Task 1 主计划尚未编写和确认；这避免任务状态领先于前置门。

## “十分详细”如何变成可检查合同

详细度不按字数判断，而按七类信息是否完整：范围、切片、文件/API/状态、Mock 与跨端策略、测试矩阵、平台证据、风险/回滚与四门。任何一类缺失或仍有未裁决占位符，都不能开始 Task 1 业务编码。

## 工作树和备选切换

OpenCode 只写 `~/code/Kuikly`，Codex 只写 Windows 仓库；两者通过功能分支交接。Task 1 切到 OpenCode 备选，或 Task 2 切到 Codex 备选，都要先停止当前写入者、记录阻塞或用户要求，并由用户确认，避免双写和缓存交叉污染。

## 限制

- 本报告证明规则已经统一，不证明 Task 1 详细计划已经完成。
- 本报告不启动 OpenCode，也不证明 Task 2 已进入开发。
- ADR-006 的旧文本保留用于解释历史，当前行为以 ADR-009 为准。
